# IssueからPRまで相談して進める

既存Issueを一つ選び、ユーザーとの会話で実装範囲とPRの内容を決める。最終的に、ユーザーが手元で動作確認できるPRコメントの直接リンクを渡す。日本語で相談・報告する。

## 相談の進め方

- Issueの選択、ユーザーに見える挙動や範囲の判断、公開するPRの内容を相談する。会話で既に決まった事項は聞き直さない。
- 質問がある場合も、その回答に依存しない調査・準備・検証は進める。回答が必要な決定は返答を待ち、無回答を同意と扱わない。
- 通常の実装手順や可逆的な修正は合意した範囲で進める。新しい要件や大きな設計変更が必要になったら、具体的な選択肢と影響を提示する。
- スキルの作成・編集だけを依頼された場合は、この開発フローを実行しない。

## 1. Issue候補を出して一緒に選ぶ

1. 対象リポジトリとGitHubのowner/repoを確認する。適用される`AGENTS.md`、`README.md`、開発ガイド、既存の作業状態を読む。
2. GitHub接続ツールまたは`gh`でopen Issueを取得する。候補の本文・コメント・ラベル・関連PRを読み、着手状況と依存関係を確認する。ラベルがないことだけを根拠に未着手と断定しない。
3. ユーザーの条件を優先し、条件がなければ目的と受け入れ条件が明確で、他の作業と衝突しにくいIssueから少数の候補を提示する。候補ごとに番号・タイトル・URL、変更の概要、選ぶ理由、規模感、未解決の依存や不明点を短く添える。優先度が根拠なく決まっているかのように表現しない。
4. 推奨候補を示し、ユーザーが一つ選ぶのを待つ。番号・URLを既に指定された場合は、そのIssueを読み直し、選択を繰り返し求めない。
5. 実装前に、目的、対象範囲、期待する挙動、受け入れ条件を具体化して共有する。選定時の会話でここまで決まっていればそのまま進める。

## 2. リポジトリ直下の.worktreeに作業場所を作る

- `git worktree list --porcelain`とGit状態を確認する。同じIssueの既存worktreeがある場合は、ブランチ・作業内容・未コミット変更を確認して再利用できるか判断する。他の作業中のworktreeに混ぜない。
- 保存先はメインのリポジトリ直下の`.worktree/`配下とする。worktree内から実行する場合は、Gitの共通ディレクトリとworktree一覧からメインの場所を確認し、`.worktree`を入れ子にしない。
- ブランチ名はリポジトリの命名ルールを優先する。IroMapでは修正も含めて`feature/issue-123-short-topic`のように`feature/*`とする。baseはリポジトリの運用またはリモートのデフォルトブランチから確認する。
- 現在のリポジトリにworktree作成用のエントリーポイントがあれば、その仕様と出力先を読んで利用する。IroMapでは`worktree:add`が定義されている場合、`pnpm run worktree:add <branch> <base>`の実装を確認する。未導入なら`git worktree add -b <branch> <absolute-path> <base-ref>`を利用する。
- ブランチの存在だけでworktreeの存在を判断しない。名前やフォルダが衝突したら既存内容を確認し、別名の選択または再利用を相談する。既存フォルダを上書きしない。
- `.worktree/`がGit追跡から除外されているか確認する。共有設定を変える必要がなければローカルのexcludeを使う。
- 作成したworktreeの`AGENTS.md`と開発手順を読み、依存関係やGit hooksを設定する。ルート、絶対worktreeパス、ブランチ、base、セットアップ結果を報告する。

## 3. 実装して確認できる状態にする

- 合意したIssueの範囲をworktree内で実装する。必要な仕様・設計・受け入れ手順も同期する。IroMapのSDD運用はそのcheckoutのREADMEと開発ガイドに従う。
- リポジトリが要求するチェックと、変更に適した検証を実行する。成功・失敗・未実行を区別し、結果の根拠を記録する。
- 差分を見直し、無関係なファイルや生成物、他者の変更を含めない。コミットは目的ごとにまとめ、対象ファイルを明示してstageする。
- ユーザーに、実装後の挙動と実際の差分に沿ったPRタイトル・本文案、検証結果、手元で確認してほしい点を提示する。PRテンプレートがあればそれに沿って日本語で書く。Issueとの関連を明記し、完了条件を満たす場合にclosing keywordを使う。

## 4. 会話で決めた内容をDraft PRにする

- PRの内容をユーザーと調整し、既に合意している内容は再承認を求めない。相談が未完了なら、差分と本文案を確認できる状態にして返答を待つ。
- PR作成と確認コメント投稿を含む実行依頼がある場合にpush・作成・投稿する。ローカルの案や調査だけの依頼を公開の許可に広げない。
- head/baseと既存PRを確認する。新規PRはDraftで作成し、同じ作業のPRが既にあればその状態と本文を読み、重複作成せず合意した更新を行う。
- `gh`で複数行のPR本文・コメントを扱う場合はUTF-8の一時ファイルを書き、`--body-file`で渡す。GitHub操作が失敗・タイムアウトしたら実際の状態を取得してから再試行し、重複PRや重複コメントを避ける。
- 作成したPRのURLを取得する。Codexの`attach_artifact`が使える場合はPRをこのタスクに添付する。既存PRを更新する場合も同様に添付する。

## 5. 動作確認コメントを投稿して直接リンクを渡す

PR本文とは別に、ユーザーが動作確認に使えるコメントをPRの会話欄に投稿する。少なくとも次を含める。

- 対象Issueと変更の概要。
- 確認対象のブランチ・コミットとローカルworktreeの場所。ユーザーが公開先に載せたくない情報は省く。
- セットアップ・起動方法。確認したプレビューURLがある場合はそのURL。
- 番号付きの操作手順と、各操作で期待する結果。
- エージェントが実行したチェックの結果、およびユーザーに確認してほしい未確認事項。ユーザーによる確認項目は未チェックのままにする。

`gh pr comment <pr> --body-file <file>`などで投稿し、投稿結果またはGitHub APIからそのコメントの`html_url`を取得する。リンク先が該当PRと投稿内容に一致することを確認する。PR全体のURLだけで済ませず、`#issuecomment-...`を含む実在する直接リンクを渡す。取得できなければ投稿状態を説明し、URLを推測しない。

最終報告では、**動作確認コメントのリンク**を最初に示し、PRリンク、実装の要点、検証結果、worktreeとブランチ、次に確認してほしいことを簡潔に添える。

## 6. ユーザーの動作確認に対応する

- コメントのリンクを渡したらユーザーの確認を待つ。手元確認待ちであることを明示し、勝手に確認済みとしない。
- 指摘が来たら、同じworktreeとPRで修正・検証し、実際の変更に合わせてPR本文と確認手順を更新する。コメントの再投稿は変更内容に応じて判断し、更新後の直接リンクを共有する。
- このフローの引き渡しは「PRと確認コメントが作成され、ユーザーにリンクが届いた」状態。マージ、Issueの手動close、worktree・ブランチの削除は別の依頼を受けてから行う。
