# Color Reassessment: 観察面を基準にした配色の再検討

## 状態と目的

- 状態: A案を実装し、修正後の実画面をユーザーが承認済み。以下の各案は比較時の検討記録。採用値はtokens.jsonを参照。
- 背景: 紺のUIとチャコールの観察面が別の塊に見え、キューブ・断面の高彩度の色とも調和していないというユーザー指摘。
- 目的: 写真の色を読むための環境と、桜・夕紺の印象を両立させる。
- 既存の色値は比較の基準として保持する。Noto Sans JP・本文字間0.04emの決定はこの再検討で変更しない。

## 現画面からの診断

- 周囲: #041A35と#061D38の青みが広い面積を占める。夕景から採った色を広いUIへ展開した結果が、写真での印象と同じになるとは限らない。
- 観察面: #242424自体の良否より、青い周囲から無彩色へ急に切り替わることが問題。画像未入力時の大きな灰色面も面積として強い。
- 階層: 背景・外枠・カード・Canvasの枠が重なり、青い線が多い。操作に必要な境界と装飾的な区切りを見直す。
- 操作色: 明るい水色の画像入力と選択タブが、虹色のデータと同時に視線を引く。文字コントラストを保ちつつ、塗りの面積と用途を比較する。
- データ: 黒に近い点が暗い背景へ沈む。反対に明るい背景では白に近い点が沈む。全色の可視性を背景色一つで解決できるとは扱わない。
- 内容: 全RGBの格子と写真の点群では色の密度が異なる。空の画面だけでなく、実際の写真を入力した主要作業で判断する。
- 限界: スクリーンショットからの設計上の診断。色相の知覚変化や正確な測色を証明したものではない。

## 再設計の順序

- 写真・3D・断面を含む観察領域の明度と、必要な色の見分けやすさを比較する。
- 観察面の直近にある枠・余白・操作領域の彩度と明度を合わせる。
- その外側に、桜・夕紺の色みをどれだけ、どの面積で残すか決める。
- 操作・選択・フォーカスを必要な強さへ調整する。
- 添え色は最後に評価する。抹茶・金星のモチーフを使い切るための装飾は増やさない。

## 比較する方向

### A: 青みを抑えた夕紺と、連続した無彩色の観察領域

- 推奨する比較の起点。
- 広いUIの青の彩度を下げ、観察面との明度差も小さくする。
- 写真・3D・断面を囲む領域全体を、ほぼ無彩色の一つの環境としてまとめる。
- 夕紺の印象は外周や見出し付近、操作の限定された箇所で残す。
- 利点: データ色と周囲の競合を抑え、チャコールだけが別の箱に見える状態を減らす狙い。
- 懸念: ユーザーが望んだ青の強さを損なう可能性がある。実画面での比較が必要。

### B: 現在の夕紺を残し、観察領域の周囲を広く中立化する

- 外側の青は維持し、Canvasのすぐ外側も無彩色にする。
- 操作と図を個別の箱にせず、観察する領域として面を連続させる。
- 利点: 夕紺の方向を保った比較ができる。
- 懸念: 中立の領域がさらに大きな別の塊に見える可能性がある。枠・余白も同時に確認する。

### C: 青みを含む観察面

- 比較用。推奨を先に確定しない。
- 周囲との色相のつながりは作りやすいが、データ直近の色付き背景が分析体験に与える影響を検討する必要がある。
- 見た目の統一だけを理由に採用しない。既存の無彩色の観察面という設計契約を変更する判断になる。

## ライトモードへの適用

- 桜でも、ピンクの広いUIと無彩色の観察面の関係を同じ観点で比較する。
- 白に近づけることだけで解決しない。桜の色み、観察面、境界の明度差を一体で調整する。
- ライトとダークを同じHEX値の反転で作らない。

## 比較条件と採否

- 同じ写真・同じ色空間・同じ回転・同じ断面値・同じ点の数と大きさで比べる。
- 夕景、肌や自然物、低彩度、白黒、高彩度を含む写真で確認する。写真データは公開しない。
- 画像未入力時と入力後を分けて確認する。大きなモニターでの面積効果も確認する。
- データRGBを変更したり、候補ごとに点群を薄めたりして配色をよく見せない。
- 判定: 写真と点群へ自然に視線が向くか、異なる色の箱が貼り付いた印象が減るか、暗部・明部の点と選択を追えるか、操作を識別できるか。
- コントラスト検査の合格と、画面全体の調和の承認を分ける。
- 採用: A案。細い表示枠、描画情報の表示切替、上端の修正を含む仕上がりをユーザーが承認した。

## 参考

- [ICC: Display calibration](https://www.color.org/displaycalibration/): 観察環境が画像の見え方へ影響するという一般的背景。IroMapの具体的なUI配色を指定する規格ではない。
- 各案の評価と推奨順はIroMapの画面に対する設計仮説であり、ICCによる推奨ではない。
