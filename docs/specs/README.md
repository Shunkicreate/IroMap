# Specs README

`docs/specs/` は機能単位の仕様セットを管理するフォルダです。

- 進捗整理: `acceptance-status.md`（spec受け入れ条件に対する達成状況）

## 意図

- 1 機能 = 1 ディレクトリで要求から実装計画まで追跡可能にする
- `spec -> design -> tasks -> test-cases` の整合を維持する
- 技術MVP（基盤）と機能MVP（ユーザー価値）を分けて管理する

## ディレクトリ命名

- `<feature-name>`
- 例: `slice`、`workbench-information-architecture`
- 機能名を固定し、同じディレクトリの仕様を更新する。年月付きディレクトリ、版別の複製、移行用の別名は作らない。
- 仕様の現在の内容を正本にする。変更履歴はGitで確認し、日付別の管理台帳を増やさない。

## 各機能ディレクトリの標準構成

- `spec.md`: 要求定義（What）
- `design.md`: 実現方式（How）
- `tasks.md`: 実装計画（Work items）
- `test-cases.md`: 受け入れ観点
- `notes.md`: 未決事項・補足メモ

## 推奨フォーマット

以下は現在の機能仕様で使用するテンプレート。未着手のログイン・ユーザー登録の仕様は管理しない。

## 書き方の意味

- `spec.md` は「何を満たすか」を定義する
- `design.md` は「どう満たすか」を定義する
- `tasks.md` と `test-cases.md` は要求 ID に紐づける
- `tasks.md` の `## テスト` チェックは「テストケース定義＋対応テストコード作成済み」を示す

## 情報設計と表示文言

- 正本: `workbench-information-architecture/information-architecture.md`、`glossary.md`、`ui-copy.md`。
- 情報整理はH1〜H5とリストで表し、目的・背景・重要度・開示区分・設計上の文言IDを定義する。
- 操作と状態の正本は `workbench-information-architecture/state-transitions.md`。同じ情報要素IDに操作・前提・変更・保持・結果を結びつける。図は連動を補助する。
- 用語集と標準表示文言に情報・状態設計と実装が従う。既存コードの名前・辞書を設計の正本にしない。
- 実装のパス・辞書キーは下流の `implementation-map.md` で管理する。設計ファイルはコードの存在や実装キーの命名に依存しない。
- 要素と文言の対応は双方向で管理する。表示文言以外のコピー項目名・直書きの文言は補助文言IDで区別する。
- `pnpm run check:information`: 文書構造、必須項目、設計ID、変数、用語の対象、全情報単位の操作分類、リンク、日付付きspec名を検査する。実装と実装対応は読み込まない。
- `pnpm run test:information`: 検査処理が不整合を検出できることを確認する。webの依存関係をインストールして実行する。
- `pnpm run check:information:implementation`: 実装対応を通じて、実装が標準文言に従うか照合する。未対応・参照ファイル不足・キー不足・ja/enの未反映を実装側の差分として報告する。
- 設計を先に変更し、実装が追いつくまで実装照合がエラーになることを許容する。差分を報告し、合っていない状態を合格と扱わない。
- 終了コード: 0は一致、1は文書不整合・実行不能、2は実装との差分。CIの実装照合は参考情報として実行し、設計検査と検査処理のテストは必須とする。
- 実装完了時は担当範囲の差分を解消する。未着手の設計差分を既存文言への差し戻しや検査除外で隠さない。
